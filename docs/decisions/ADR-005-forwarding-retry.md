# ADR-005：异步转发 + 有界重试 + 超时 Unknown（不自动重试）

- 状态：Accepted
- 日期：2026-10-28

## 背景

P2/P3 的转发在 IPP `Send-Document` 请求内同步执行，只尝试一次：

- 目标打印机慢/离线时，Windows 打印请求被长时间占用；
- 失败后没有重试；
- 失败/超时无法区分，可能重复打印。

P4 要求：失败重试、幂等、超时处理、人工确认、目标覆盖。

## 决策

### 1. 捕获与转发解耦

- `PrintJobPipeline` 只做：保存文档 → 归一化属性 → 计价 → 路由 → 写 SQLite → 入队；
- `ForwardingWorker` 在后台串行消费队列；
- IPP 请求立即返回成功，不等待目标打印机和重试延迟。

### 2. 有界重试

- 默认最多 4 次尝试（首次 + 3 次重试）；
- 重试间隔默认 2s / 10s / 30s，可配置；
- 每次尝试有独立超时（默认 30s）；
- 明确失败（连接拒绝、IPP 错误、4xx/5xx）才自动重试；
- 重试期间状态为 `Priced`，`StatusReason` 记录第几次失败；UI 显示“待转发”。

### 3. 超时 = Unknown，不自动重试

- 超时可能意味着目标已经收下任务，只是响应丢失；
- 自动重试可能重复打印，因此超时后状态置为 `Unknown`，不自动重试；
- 用户可在 UI 里手动“重试”，自行承担重复风险；
- 失败重试有上限，避免无限循环。

### 4. 幂等

- IPP 转发的 `job-name` 追加 `[PrintPal:<JobId>]`；
- 重试使用同一个 JobId，便于目标/日志关联；
- Raw 9100 没有作业名/协议元数据，无法在协议层幂等；文档明确此限制；
- 超时场景不自动重试，是比“依赖打印机去重”更可靠的保护。

### 5. 人工确认 / 目标覆盖

- `AutoForward=false`：捕获/计价/路由后状态为 `Held`，不自动转发；
- UI 的“转发/重试”按当前目标入队；
- UI 的“选择目标转发”可覆盖目标打印机后入队；
- `Succeeded` 任务不可重试（防止误重打）；`NeedsReview` 不可转发（没有有效计价）；
- 应用启动时只恢复 `Priced` 且已有目标的任务；`Held/Failed/Unknown` 需人工操作；
- 崩溃/强杀残留的 `Forwarding` 启动时置 `Unknown`，不自动重试。

## 后果

正面：

- Windows 打印请求快速返回，目标离线不影响用户打印体验；
- 失败可自动恢复；
- 超时不会静默重复打印；
- 人工确认/目标覆盖满足打印店场景。

负面：

- 后台串行 worker 在重试延迟期间会阻塞后续任务；P7 可增加并发/队列持久化；
- `Unknown` 需要用户判断；
- Raw 9100 无幂等元数据；
- 重试次数/间隔暂未暴露到 UI 设置。

## 状态流

```
Captured → Priced → Forwarding → Succeeded
                    ↓ 失败且可重试
                  Priced → Forwarding → ... → Failed
                    ↓ 超时
                  Unknown（不自动重试）
AutoForward=false → Held（人工转发）
```

## 备选方案

| 方案 | 不选原因 |
|---|---|
| 继续同步重试 | 阻塞 Windows 打印请求，重试延迟不可接受 |
| 超时也自动重试 | 可能重复打印/重复计费 |
| 无限重试 | 目标长期离线时无限循环 |
| 依赖打印机 job-name 去重 | 不同打印机支持不一致，不可靠 |

## 验证

- `AgentPipelineTests`：重试成功、达到上限失败、超时 Unknown、人工确认、目标覆盖、崩溃残留恢复；
- P4 UI 实测：`--no-auto-forward` 捕获为 Held，点击“转发/重试”后成功；
- FakePrinter 日志可见 `job-name` 带 `[PrintPal:<JobId>]`。
